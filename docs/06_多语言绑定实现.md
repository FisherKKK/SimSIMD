# SimSIMD 多语言绑定实现详解

> 本文是 SimSIMD 讲解系列第六篇，深入解析 C 动态分发库、Python CPython 绑定、以及 JavaScript/Rust 绑定的实现机制。

---

## 一、架构概览

SimSIMD 的多语言支持分为两层：

```
用户代码（Python / JavaScript / Rust / Go / Swift）
          ↓
语言绑定层（python/lib.c, javascript/lib.c, rust/lib.rs）
          ↓
动态分发层（c/lib.c）— SIMSIMD_DYNAMIC_DISPATCH=1
          ↓
头文件实现（include/simsimd/*.h）— 所有 SIMD 实现
```

## 二、动态分发库（c/lib.c）

### 2.1 设计目标

`c/lib.c` 实现了一个**运行时自动选择最优算法**的机制。编译时无需知道目标 CPU，程序启动后自动探测并选择最快的实现。

### 2.2 核心机制：惰性初始化（Lazy Initialization）

```c
// c/lib.c 第 60-80 行

// 展开宏：为每个函数生成一个动态分发版本
#define SIMSIMD_DECLARATION_DENSE(name, extension)                    \
    SIMSIMD_DYNAMIC void simsimd_##name##_##extension(                \
        simsimd_##extension##_t const *a,                             \
        simsimd_##extension##_t const *b,                             \
        simsimd_size_t n,                                             \
        simsimd_distance_t *results) {                                \
                                                                      \
        // 用 static 局部变量缓存函数指针（只初始化一次）
        static simsimd_metric_dense_punned_t metric = 0;              \
                                                                      \
        if (metric == 0) {  // 第一次调用时初始化                     \
            simsimd_capability_t used_capability;                      \
            // 查询：对于这个度量+数据类型，最优的实现是什么？
            simsimd_find_kernel_punned(                                \
                simsimd_metric_##name##_k,    // 度量类型             \
                simsimd_datatype_##extension##_k, // 数据类型         \
                simsimd_capabilities(),        // 当前 CPU 能力       \
                simsimd_cap_any_k,             // 接受任何能力的实现   \
                (simsimd_kernel_punned_t *)&metric,  // 输出：函数指针 \
                &used_capability               // 输出：选择了哪种能力 \
            );                                                         \
            // 如果没有找到合适的实现，返回 NaN
            if (!metric) {                                             \
                *(simsimd_u64_t *)results = 0x7FF0000000000001ull;     \
                return;                                                \
            }                                                          \
        }                                                              \
        metric(a, b, n, results);  // 调用找到的最优函数              \
    }
```

**惰性初始化的工作流程**：

```
第1次调用 simsimd_cos_f32(a, b, n, &result)：
  1. 检查 metric == 0 → 是的
  2. 调用 simsimd_capabilities() → 得到 CPU 支持的能力集合
  3. 调用 simsimd_find_kernel_punned() → 返回最优函数指针
     （例如：如果 CPU 支持 AVX512，就返回 simsimd_cos_f32_sapphire）
  4. 把指针存入 static metric（此后不再需要初始化）
  5. 调用 metric(a, b, n, &result)

第2次及后续调用：
  1. 检查 metric == 0 → 不是（已经初始化）
  2. 直接调用 metric(a, b, n, &result)
  ← 只多了一次指针比较，开销可忽略不计
```

**打比方**：就像一个聪明的导航 APP，第一次使用时需要定位和计算路线，之后就记住了，直接复用。

### 2.3 NaN 的表示

```c
// 当找不到合适的实现时：
*(simsimd_u64_t *)results = 0x7FF0000000000001ull;
//                           ↑
// IEEE 754 中 signaling NaN（信号 NaN）的位模式
// 0x7FF0000000000001 = 0 111 1111 1111 1111...0001
//                       ^  指数全1              ^ 尾数非零 = NaN
```

这确保了失败时返回一个合法的 IEEE 754 特殊值，而不是未定义行为。

### 2.4 平台特定的编译控制

```c
// c/lib.c 第 23-52 行

// macOS 只支持 NEON 和 Haswell（Apple Clang 限制）
#if !defined(SIMSIMD_TARGET_NEON) && (defined(__APPLE__) || defined(__linux__))
#define SIMSIMD_TARGET_NEON 1
#endif

// SVE 只在 Linux 上可用（macOS 不支持 SVE 内联汇编）
#if !defined(SIMSIMD_TARGET_SVE) && (defined(__linux__))
#define SIMSIMD_TARGET_SVE 1
#endif

// Genoa（BF16）和 Sapphire（FP16）只在 Linux 上编译
#if !defined(SIMSIMD_TARGET_GENOA) && (defined(__linux__))
#define SIMSIMD_TARGET_GENOA 1
#endif
#if !defined(SIMSIMD_TARGET_SAPPHIRE) && (defined(__linux__))
#define SIMSIMD_TARGET_SAPPHIRE 1
#endif
```

**为什么 macOS 受限？** Apple Clang 不支持某些 GCC 的 target 属性（如 AVX512 的新变体和 ARM SVE），所以只开启 Apple Clang 确定支持的选项。

## 三、Python 绑定（python/lib.c）

### 3.1 为什么不用 PyBind11 或 NanoBind？

`python/lib.c` 开头的注释给出了详细解释：

```
问题：PyBind11 / NanoBind / SWIG 等高级包装：
  - 使用动态数据结构映射回调，不利用 CPython 的最优 API
  - PyArg_ParseTupleAndKeywords 需要动态解析格式字符串，"不可能快"
  - 对于低延迟操作（向量距离计算），这些开销是不可接受的

解决方案：直接使用 CPython API 的 METH_FASTCALL
```

**实际影响**：对于一个计算只需 100ns 的函数，如果参数解析需要 500ns，那绑定开销占总时间的 83%！

### 3.2 METH_FASTCALL：快速调用约定

```c
// 传统方式（慢）：
static PyObject* cdist(
    PyObject *self,
    PyObject *positional_args_tuple,   // 元组对象
    PyObject *named_args_dict) {       // 字典对象
    // 需要动态解析格式字符串 "OO|s$Kss"
    PyArg_ParseTupleAndKeywords(...);
}

// METH_FASTCALL（快）：
static PyObject* cdist(
    PyObject *self,
    PyObject * const *args_c_array,     // C 数组，直接访问！
    Py_ssize_t positional_args_count,   // 位置参数数量
    PyObject *args_names_tuple) {       // 关键字参数名称元组
    // 直接用 args_c_array[0], args_c_array[1] 等访问参数
    // 无需动态解析！
}
```

### 3.3 Buffer Protocol：零拷贝数据交换

**Buffer Protocol** 是 Python 中实现零拷贝数据共享的标准协议。NumPy、PyTorch、TensorFlow 的数组/张量都实现了这个协议。

```python
# Python 侧：
import numpy as np
a = np.array([1.0, 2.0, 3.0], dtype=np.float32)
b = np.array([4.0, 5.0, 6.0], dtype=np.float32)

# 调用 simsimd.cosine(a, b)
# C 代码通过 Buffer Protocol 直接访问 a 和 b 的内存，不做拷贝！
```

```c
// python/lib.c 中处理输入向量的结构体
typedef struct TensorArgument {
    char *start;           // 数据的起始地址（直接指向 NumPy/PyTorch 的内存）
    size_t dimensions;     // 维度数
    size_t count;          // 元素数量
    size_t stride;         // 步长（字节）
    int rank;              // 秩（1D 或 2D）
    simsimd_datatype_t datatype; // 数据类型
} TensorArgument;
```

**零拷贝的实现**：
1. Python 调用 `simsimd.cosine(a, b)`
2. C 代码通过 `PyObject_GetBuffer(a_obj, &buffer, PyBUF_SIMPLE)` 获取缓冲区信息
3. `buffer.buf` 直接指向 NumPy 数组的内部数据
4. C 代码直接对这块内存做计算，无需任何拷贝！

### 3.4 数据类型字符串映射

这是 SimSIMD Python 绑定最复杂的部分之一：不同框架对同一类型有不同的字符串表示：

```c
// python/lib.c 第 155-200 行
simsimd_datatype_t python_string_to_datatype(char const *name) {
    // f32：NumPy/PyTorch/自定义 格式 各不同
    if (same_string(name, "float32") ||  // PyTorch/TF 格式
        same_string(name, "f32") ||      // SimSIMD 自定义
        same_string(name, "f4") ||       // NumPy 格式（4字节浮点）
        same_string(name, "<f4") ||      // NumPy 格式（小端）
        same_string(name, "f") ||        // struct 模块格式
        same_string(name, "<f"))         // struct 模块格式（小端）
        return simsimd_datatype_f32_k;

    // bf16：特别麻烦，TensorFlow 用 'E' 表示
    // 注释说："其确切格式未定义，但 TensorFlow 使用 'E'"
    else if (same_string(name, "bfloat16") || same_string(name, "bf16"))
        return simsimd_datatype_bf16_k;
    // ...（TensorFlow 的 'E' 格式需要特殊处理）
}
```

**这解决了一个真实存在的生态系统问题**：PyTorch、TensorFlow、NumPy、JAX 各自有不同的类型字符串约定，而 SimSIMD 的 Python 绑定兼容了所有这些。

### 3.5 DistancesTensor：自定义输出对象

```c
// python/lib.c 第 109-134 行

// 自定义的输出类型，实现了 Buffer Protocol
typedef struct DistancesTensor {
    PyObject_HEAD                    // Python 对象头（引用计数等）
    simsimd_datatype_t datatype;     // 数据类型
    size_t dimensions;               // 维度数
    Py_ssize_t shape[2];             // 形状（最多2D）
    Py_ssize_t strides[2];           // 步长
    simsimd_distance_t start[];      // 灵活数组（变长成员，数据存在这里）
} DistancesTensor;

// 注册 Buffer Protocol 支持
static PyBufferProcs DistancesTensor_as_buffer = {
    .bf_getbuffer = DistancesTensor_getbuffer,    // 获取缓冲区视图
    .bf_releasebuffer = DistancesTensor_releasebuffer, // 释放
};
```

```python
# Python 侧使用示例
result = simsimd.cdist(matrix_a, matrix_b, "cos")
# result 是 DistancesTensor 对象

# 可以直接转换为 NumPy（零拷贝！）
import numpy as np
result_np = np.array(result)  # 通过 Buffer Protocol，不拷贝数据

# 或者直接 memoryview
mv = memoryview(result)
```

**`start[]` 的含义**：这是 C99 的**柔性数组成员（Flexible Array Member）**。`DistancesTensor` 对象在分配内存时，会额外分配足够存放所有距离值的空间：

```c
// 分配：结构体 + n 个 f64 的空间
size_t obj_size = sizeof(DistancesTensor) + n * sizeof(simsimd_distance_t);
DistancesTensor *tensor = PyObject_Malloc(obj_size);
// tensor->start[] 就是紧跟在结构体后面的数组
```

## 五、Rust 绑定（rust/lib.rs）

### 5.1 原始 FFI（Foreign Function Interface）

```rust
// rust/lib.rs
extern "C" {
    // 直接声明 C 函数
    pub fn simsimd_cos_f32(
        a: *const f32,
        b: *const f32,
        n: u64,          // 注意：用 u64，不用 usize（ABI 兼容性）
        result: *mut f64,
    );
}
```

**为什么用 `u64` 而不是 `usize`？**

注释说："使用 u64 而不是 usize 是为了 ABI 兼容性"。在某些平台上，`usize` 的大小可能不同（32位 vs 64位），而 C 侧的 `simsimd_size_t` 被定义为 `unsigned long long`（始终是64位）。

### 5.2 Safe Wrapper

```rust
// Rust 的 trait 定义
pub trait SpatialSimilarity {
    fn cos(a: &[Self], b: &[Self]) -> Result<f64, SimsimdError>
    where Self: Sized;
}

// i8 的实现
impl SpatialSimilarity for i8 {
    fn cos(a: &[i8], b: &[i8]) -> Result<f64, SimsimdError> {
        // 检查长度
        if a.len() != b.len() {
            return Err(SimsimdError::LengthMismatch);
        }
        let mut result: f64 = 0.0;
        unsafe {
            // 调用 C 函数（unsafe，因为原始指针）
            simsimd_cos_i8(
                a.as_ptr(),
                b.as_ptr(),
                a.len() as u64,
                &mut result,
            );
        }
        Ok(result)
    }
}
```

```rust
// Rust 侧使用
let a: Vec<i8> = vec![1, 2, 3, 4];
let b: Vec<i8> = vec![5, 6, 7, 8];
let distance = i8::cos(&a, &b).unwrap();
```

## 六、动态分发的 find_kernel 机制

这是整个分发系统的核心函数，让我们理解它的逻辑：

```c
// 伪代码描述 simsimd_find_kernel_punned 的逻辑

void simsimd_find_kernel_punned(
    simsimd_metric_kind_t metric,      // 需要什么度量（cos, l2, dot...）
    simsimd_datatype_t datatype,       // 需要什么数据类型（f32, f16...）
    simsimd_capability_t capabilities, // CPU 当前支持什么（运行时检测结果）
    simsimd_capability_t preference,   // 偏好什么能力（通常是 any）
    simsimd_kernel_punned_t *kernel,   // 输出：找到的函数指针
    simsimd_capability_t *used_cap) {  // 输出：实际使用了什么能力

    // 优先级从高到低尝试：
    // （假设在 x86 上）
    if ((capabilities & simsimd_cap_sapphire_k) && sapphire支持该metric和datatype)
        *kernel = sapphire对应的函数;
    else if ((capabilities & simsimd_cap_genoa_k) && genoa支持)
        *kernel = genoa对应的函数;
    else if ((capabilities & simsimd_cap_ice_k) && ice支持)
        *kernel = ice对应的函数;
    else if ((capabilities & simsimd_cap_skylake_k) && skylake支持)
        *kernel = skylake对应的函数;
    else if ((capabilities & simsimd_cap_haswell_k) && haswell支持)
        *kernel = haswell对应的函数;
    else
        *kernel = serial对应的函数;  // 保底
}
```

**关键点**：`simsimd_capabilities()` 是在**第一次调用**某函数时计算的（通过 CPUID 或 sysctl），之后缓存在全局变量中。

## 七、Python 包的 CPU 能力缓存

```c
// python/lib.c 第 136-137 行
// 模块加载时就计算 CPU 能力，存入全局变量
simsimd_capability_t static_capabilities = simsimd_cap_serial_k;
```

```c
// 在模块初始化函数中：
static struct PyModuleDef module = {
    PyModuleDef_HEAD_INIT,
    .m_name = "simsimd",
    // ...
};

PyMODINIT_FUNC PyInit_simsimd(void) {
    // 启动时立即检测 CPU
    static_capabilities = simsimd_capabilities();
    // ...
}
```

这样 CPU 能力检测只在 `import simsimd` 时执行一次，之后的所有调用都用缓存的结果。

## 八、跨框架兼容的挑战

Python 绑定注释中提到了一个真实的生态系统问题：

```python
# NumPy 支持 buffer protocol：
import numpy as np
a = np.array([1.0], dtype='bfloat16')  # NumPy 1.24+ 才支持
memoryview(a)  # 可以工作

# PyTorch 不直接支持 buffer protocol：
import torch
t = torch.tensor([1.0], dtype=torch.bfloat16)
memoryview(t)  # TypeError！PyTorch 张量不能直接转 memoryview

# TensorFlow 的 bf16 格式字符串：
tf_tensor = tf.constant([1.0], dtype=tf.bfloat16)
# TF 内部用 'E' 表示 bfloat16，与 NumPy 不同！
```

SimSIMD 的解决方案：
1. 先尝试 buffer protocol
2. 如果失败，尝试 `__array_interface__`（NumPy 接口）
3. 如果失败，尝试 `__dlpack__`（PyTorch/JAX 接口）

| 线程支持 | - | OpenMP（Linux） | Rayon（外部） | - |

## 十、小结

```
动态分发库（c/lib.c）的设计精髓：
  ┌─────────────────────────────────────────────┐
  │  第1次调用某函数                              │
  │    → simsimd_capabilities() 探测 CPU         │
  │    → simsimd_find_kernel_punned() 找最优实现  │
  │    → 缓存函数指针（static 变量）              │
  └─────────────────────────────────────────────┘
  ┌─────────────────────────────────────────────┐
  │  后续调用                                    │
  │    → 直接调用缓存的函数指针                   │
  │    （只比直接调用多一次指针比较）              │
  └─────────────────────────────────────────────┘

Python 绑定的关键技术：
  1. METH_FASTCALL：避免参数解析开销
  2. Buffer Protocol：零拷贝数据访问
  3. 多格式字符串映射：跨框架兼容
  4. DistancesTensor：柔性数组成员实现零拷贝输出
  5. OpenMP：Linux 上的多线程支持
```
